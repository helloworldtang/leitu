## 最严重的一条：`ConfigReader` Bean 的源链没有文档

`config-source.md` 机制段写的是 `ConfigReader.standard()` 的**三源**（系统属性 → 环境变量 → `leitu.properties`），
`INTEGRATION` §2 同样写「配置来源固定三源兜底」。而 starter 实际装配的 Bean 是**四段链**：

```
spring-overrides（命令行 / 系统属性 / 系统环境变量）
  → 宿主声明的 ConfigSource Bean（配置中心）
  → spring-files（application.properties / yml）
  → leitu.properties
```

依据：`LeituConfigAutoConfiguration.configReader(Environment, ObjectProvider<ConfigSource>)` 的构造顺序，
且仓内已有 `LeituStarterWiringTest.Environment里的键_优先于三源()` 守住这个优先级。

执行者是**反编译 `~/.m2` 里的 jar 才确认的**。这张卡的目标答案面正是 config-source ——
**照文档写不出正确答案**，这是本轮最贵的一条：文档描述的是 `standard()` 的形状，
没描述「引了 starter 之后，你拿到的是哪个 ConfigReader」。

根因可用一句话概括：`config-source.md` 的「成套答案」还停在 0.2.0 的**「starter 装配待真实痛点接入」**，
而 starter 在 0.2.1 已交付（ADR-014）——答案页那一刻起就与实现脱钩，且没有任何机器守着它。

## 第二条：任务卡的阅读面与实际所需错位

执行者原话：六个问题页里 `who-is-operating` / `allow-or-not` / `api-contract` 的两段对本次实现信息量很低

## 其余工单

1. `INTEGRATION` §1 把两种姿态的插件说明混在一起：先用 BOM import 讲「三个插件都要自己钉」，
   再说「parent 顺带拿到 compiler/surefire/enforcer」——实际用 parent 时只有 `spring-boot-maven-plugin` 要自钉；
2. 失败投影的 kind→status 映射（BUSINESS→400 / `guard.denied`→403 / SYSTEM→500 / `attributes["http.status"]` 可覆盖）
   只在代码里，`failure-response.md` §2 只说「kind→4xx/5xx」；要选 400 还是 404 的人必须查这张表；
3. `JdbcDataStoreFactory` 与 `DataSource` 是硬依赖（`@ConditionalOnBean(DataSource)`），
   验收只说「就位即可」，没说要配 DataSource；
4. 金样本 `DemoContextFilter` 是 `src/main` 里的 `@Component`，只靠一个 `@Value` 开关关着——
   照抄就会把「信任请求头」的代码路径带进生产 classpath（与任务 01 发现的开关问题同源）；
5. Boot 4 的 `@AutoConfigureMockMvc` 包名搬家未写（与任务 02 独立命中同一处）。
