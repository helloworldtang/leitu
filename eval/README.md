# eval —— AI 生产力基准（种子）

> 阶段三的实证义务：把「确定性 foundation」的主张变成可测量的数字，而不是感觉。
> 当前为**种子**：协议 + 第一条标准任务 + 参考解 + 基线记录；规模化跑批待行。

## 度量口径

| 指标 | 口径 |
|---|---|
| 完成率 | 任务验收清单全过 = 完成；任一不过 = 未完成 |
| 一次绿灯率 | 首次构建即全绿的比例（不允许迭代修复后再计） |
| 时长 | 从交底到首次提交验收的墙钟时间 |
| 歧义点 | 执行中「文档说不清、需要猜」的位置清单——每个歧义点都是框架/文档的改进工单 |

## 怎么跑一条任务

1. 给一个「全新 agent」：任务卡（`tasks/` 下）+ 本仓库只读访问；工作目录在仓库之外；
2. 按任务卡的「按序读」清单执行（顺序即执行顺序），不得阅读 `eval/reference/**`；
3. 按任务卡验收命令跑结果，登记上述四类数字。

**参考解本身也是要跑的**：`./mvnw -B -P eval verify` 会把 `reference/**` 拉进 reactor 一起验证
（CI 每次 push 都跑，见 .github/workflows/ci.yml）——它是"规则在下游真的有效"唯一可执行的证据，
一个从未被执行过的答案等于没有答案。

**任务卡改版必须 bump 版本号并在这里登记**：任务卡一改（阅读清单、验收命令、允许的输入），
判据就变了，跨版本的完成率与歧义点数**不可直接比较**。任务卡 v2 起把「允许阅读」改成「按序读」，
直接诱因是 v1 的 20 个歧义点里 15 个属于「文档已写但没被找到」——这一版要重新采一次样，与 v1 并列登记。

修订规则：**采样前可改，采样后冻结**。首次采样读数落地后，任务卡只能 bump 版本 + 重新采样，不得原地改判据。

**v2 预检（不计入基线）**：2026-10-26 一次只具备文件读取能力的隔离运行，按 v2 清单读完材料后报了 18 条规格级歧义
（最重的三条：映射对象 `ORDER_MAPPING` 全仓库无定义、`type` 的「裸点分 vs URN」两层语义混写、
示例守卫只放行 admin 却与「alice 应得 200」的验收互斥）。已逐条修进 [INTEGRATION](../docs/INTEGRATION.md) 与任务卡；
完整 18 条留痕见 [prechecks/2026-10-26-task01-v2.md](prechecks/2026-10-26-task01-v2.md)；
正式采样的完整留痕在 [runs/](runs/2026-10-26-task01-v2.md)（同目录含对照组）。
该运行**没有 shell、跑不了构建**，四个数全部无效，**不得当作基线读数**——它只证明一件事：光读材料就能筛出一批真缺陷。
