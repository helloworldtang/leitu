# ADR-013 问题"服务对外暴露了什么"的答案：不自研，集成 springdoc + knife4j

状态：已接受（2026-09-13）

## 背景

API 文档是业务开发链的最后一环（业务逻辑 → 配置 → 数据库 → 缓存 → API 文档），也是漂移最显眼的一环：文档与实现不同步、自研目录各自漂、示例与正文自相矛盾的活案例并不少见。对既有实践验尸得三条（独立论证）：

1. **自研 API 目录 / 错误码注册表 = 造轮子且易漂移**——OpenAPI 已是事实标准，再造一套目录等于双份维护；错误码无注册表各自维护，文档生成排期永远靠后；
2. **文档端点被统一响应包装污染的事故**——统一信封无差别覆盖控制器，文档端点（对外 API 表达的入口）被包进业务响应结构，UI 读不到配置而回退示例站——"非业务端点豁免"缺框架级约束；
3. **注解声明与"本库拒隐式魔法"教义的表面冲突**——本库三次拒绝注解式声明（判定链、输入验证、缓存装饰），API 文档却是注解声明的天下。

## 决策

**不自研：API 文档走 springdoc + knife4j（OpenAPI 3 事实标准）。**

- **声明方式 = 注解 + 扫描**（springdoc 的 @Operation 系注解）。与教义的和解判别式：**约定属于谁、违反被谁抓住**——教义拒绝的是本库**自造**的隐式魔法约定（每个约定要能指着本库测试说"违反会被谁抓住"）；消费生态标准约定不违（同用 JDK 注解不算魔法）——springdoc 注解是 OpenAPI 标准的 Java 表达，其约定由生态守护，本库不新增任何自有魔法。
- **人读面 = knife4j UI**（不自研 Markdown 渲染器——UI 已是人读标准答案）。
- **leitu 的增值点在 starter 接线（待建，随 adapter/starter 层开启另行规划）**：
  1. FailureNotice → problem+json 的 schema 对齐（ADR-011 投影的落地处）
  2. traceId 响应头提示（失败交代的关联键进文档示例）
  3. 判定链 action 与 operationId 的点分同源对齐建议（对外目录与判定动作同名）
  4. 文档端点豁免统一包装的框架级约束（验尸教训 2 的防再犯）
- catalog 状态 **drafted** = 答案已成文、实现随 starter 层落地——文档先行的诚实态（ADR-006）。

## 业界对照

OpenAPI 3（对外接口表达的事实标准）；springdoc-openapi（Spring Boot 生态主流，注解扫描生成）；knife4j（中文化增强 UI，国内主流）；swagger-ui（标准 UI）。

## 后果

- 本条无代码件——集成代码 = 第一个 starter 模块，开启 adapter/starter 层是整套架构决策（宿主版本管理 / BOM / 模块布局），另行专门规划；
- 业务开发链以"决策已定、实现待建"闭合：8 条 answered + 1 条 drafted；
- 接线时四条对齐点是 leitu 在文档域的全部增值——超出部分不承诺（承诺纪律）。

**被拒绝的备选**：自研 ApiCatalog 操作目录（造轮子 + 双份漂移）；自研 Markdown 渲染器（knife4j UI 已是人读面）；错误码注册表（failure-response 已定 type 点分标识，无中心码表）；HTTP 200 + body code 集成（ADR-011 已拒）；在 core 定义传输绑定的 OpenAPI 子集（传输投影不进 core——FailureNotice 同判）。
