# ADR-005 问题"允许吗"重构为判定链

状态：已接受（2026-09-07）

## 背景

"这个操作允许吗"最初按权限窄接口设计。复审发现：能对一次访问说"不"的来源远不止权限——功能权限、数据权限、限流、配额、熔断、维护窗口、风控。它们发生在管道的**同一时刻**（放行检查）、产出**同一形状的答案**（允许/否决 + 原因 + 重试语义）、走**同一错误通道**。

## 决策

标准答案 = **判定链（Guard Chain）**：一串可插拔 Guard，任一可否决，输出统一 Decision。

- **Guard SPI + Decision{verdict, reason, retry}**；链的组装与执行在 core（PEP 的形状），Guards 是答案侧（PDP 的角色）
- **双执行点，同一协议**：入口判定链（进来的请求：权限/限流/风控）/ 出站判定链（调出去的请求：熔断/预算）
- **安全默认**：deny-by-default；否决必须带"为什么 + 怎么办"（错误即教程）
- **限流不再是独立管道问题**，并入判定链为 guard（收敛式修正：同问题合并，不拆条件分支）
- **能力拆分**：identity（"谁在操作"的成套答案）与 access（判定链用法 + 权限类 Guards）为两个 capability——变化原因不同（换 IdP 不动判定；改判定不动身份源），且身份与判定在业界是两个独立演化的标准生态
- 限流/配额为 **guard 型能力**，走准入流程先进 experimental

## 业界对照

XACML 的 PDP/PEP 分离是正典；Spring Security 内部 AuthenticationManager 与 AccessDecisionManager 分立，与本设计同构；零信任架构以 PDP 为中央仲裁者；Permit.io 的 PDP 内置限流，佐证"限流属于判定层"。

## 待定（实现前决）

- Guard 注册顺序语义：首否决即断 vs 全量评估并报
- 判定链与网关层防护的边界表述（纵深关系，不互替）
