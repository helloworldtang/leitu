# ADR-002 core 职责与 core/capability 边界

状态：已接受（2026-09-07）

## 背景

core 与 capability 的边界是本项目最大的结构争议。单纯"运行时问题 vs 业务能力"的表述不完整：core 实际承担两件事——执行管道的端口面、跨模块协作的调度机制；模块加载与生命周期委托宿主。

## 决策

**core = 执行管道的端口面（必答问题的唯一接口）+ 跨模块协作的调度机制（OperationDispatcher）。**

**边界三测试**（一条归属的准入判据）：
1. 管道测试：框架机器自身消费它吗？
2. 必然测试：它整个不存在，框架还能跑吗？（能跑 → capability）
3. 形状测试：它是一个"问题"，还是一个"领域"？（问题 → core，领域 → capability）

**变化原因分层**：core ≈ 冻结（管道形态二十年未变）；capability 以年计（领域认知/技术景观）；adapter 以月计（中间件版本）；starter 跟随宿主。变化原因不同才分层。

**必答题三段交付**：形状（core 窄接口）+ 兜底（core 内置默认值）+ 成套答案（capability + starter 默认接线）。**答案的完整单位是目录条目，不是 artifact。**

**分维度默认值**：无害维度（缓存/事件/存储）可 Noop 零开销降级；安全维度（授权）deny-by-default + 显式放行；观测维度给最小可用实现（日志级）。Noop 一刀切的降级教义废除——对授权 Noop 等于默认放行，是安全反模式。

## 被拒绝的备选

- core 只放"最窄提问接口"（无兜底、无成套）：交付的是问题的形状而非答案，使用者需三处拼装，与标准答案库定位相悖
- 事务同步归属 core：主消费方是数据能力，管道测试弱通过——列为验尸案例，待 L1 复核（catalog 条目 transaction-boundary）

## 业界同构

OSGi Framework/Compendium、JPMS java.base、微内核系统的机制/内容之分——三个年代三个领域收敛到同一条边界。
