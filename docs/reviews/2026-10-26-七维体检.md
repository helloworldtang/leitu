## 1. 答案边界 · 4.0

证据：

- 8 份问题页 8/8 有 `## 四、边界`，且边界写得具体（例：cache「进程内承诺同键只装一次，分布式不承诺——跨进程互斥是 lock 条目的事」）。
- GLOSSARY 用「不叫 X」句式在词层堵口（DataStore 不叫 Repository、不承诺聚合根与派生查询）。
- ADR-004 是一次性的硬删除：部署拓扑目标整体移除，且连带把答案从"有条件"变"无条件"。

扣分点：

- **只有"答了什么"，没有"永不答什么"**。catalog 20 条里 11 条 `open`，但 `open` 混装了两种东西——"还没做"（transaction-boundary）与"不该由我答"（module-collaboration 之外的部署形态）。读者无法区分 backlog 与 out-of-scope。
- `access` 与 `allow-or-not` 两个条目共用 `docs/problems/allow-or-not.md`：1 页对 2 个 id，按 id 找文档的人会以为自己走错了。

## 2. 答案形状 · 4.5

证据：

- 九条 answered 全部满足五件套；`CatalogIntegrityTest`（6 个用例）强制文件真实存在、枚举合法、依赖图无孤儿、全仓相对链接有效。
- 九条各有可运行金样本（`examples/` 9 个模块进 reactor，CI 一起验证）。

扣分点：

- **四段式没有被机器守**。`DocsConsistencyTest` 管的是"不写死测试数量 / ADR 范围 / Central 元数据 / 版本闸门"，不管问题页的骨架。今天 8/8 齐是靠习惯，明天新人加一条就可能只有三段。
- 「取舍」段的深度不均：cache 写了并发与分布式边界，部分页面只列了选型对比，没写"用了会付出什么"。

## 3. 可消费性 · 3.0 ← 最大杠杆

证据：

- 最小学习集 4 个文件（GLOSSARY + catalog + 一页范本 + ADR 索引）合计约 3.0 万字符 / 650 行；`check-skill.mjs` 保证 SKILL.md 的 17 条路径有效、9 条 answered 全覆盖、版本与根 pom 相等（实测通过：`0.2.1`）。
- eval 任务 01 的独立采样：完成 6/6、一次绿灯、5 分 33 秒——**消费链路本身是通的**。

扣分点（本次最有价值的一条）：

- **20 个歧义点里 15 个是 A 类：文档已写、但没被找到**。执行者的阅读路径是先问题页再翻源码，跳过了 README 接入段；而 `maven.compiler.release`、`-parameters`、六列列名恰好全在那一段。
- 根因是结构性的：同一件接入事实散落在「问题页 + README + 金样本」三处，任务卡只给了"允许阅读清单"，没给"按序读哪三处"。**AI 的失败模式不是读不懂，是读漏。**
- 侧面证据：`access` 找不到自己的页面（见 1），说明路由表是按"条目"而非按"人会怎么问"组织的。

## 4. 机器守护 · 4.5

证据（本次实跑）：

- `./mvnw verify` → BUILD SUCCESS，12.3 秒，260 条用例全绿（9 个库模块 + 9 个金样本）。
- 四道守门人各管一段：ArchUnit 边界规则（Spring 只在 starter/adapter）、CatalogIntegrity（五件套与链接）、DocsConsistency（数字不写死 / ADR 范围 / Central 元数据 / 版本闸门顺序）、`check-skill.mjs`（4 条断言，锚点未命中一律报错而非静默通过）、`views.md` 由 `ExportArchitecture` 生成 + CI staleness 检查。

扣分点：

- **"文档宣称"与"实现"的一致性没有守卫**。README 说过"引依赖即得 `/v3/api-docs`"，而 starter 把 springdoc 标了 `optional`——这条漂移是靠人复核 eval 报告抓到的，机器全程绿灯。这是最贵的一类红灯，因为它的方向是"文档在主动误导"。

## 5. 落地成本 · 4.5

证据：

- core 零框架依赖，starter/adapter 分家，ADR-014/015 把装配层单独立法。
- eval 冷仓库验收（不是自述）：空本地仓库重跑，leitu 制品全部解析，jar 的 SHA-1 与 Central 官方逐一对齐——"引依赖即用"在真冷仓库下成立。

扣分点：

- B 类真缺口 5 条里 3 条属于"接入面不全"：`leitu.openapi.*` 属性没有用户面属性表、只引 starter 的依赖清单不完整、"无认证体系时怎么把服务跑起来"无示范。都是 5 分钟能补的一页纸，但现在要 AI 自己猜。

## 6. 实证 · 2.5

证据：

- 四项指标口径清楚（完成率 / 一次绿灯率 / 时长 / 歧义点），且登记时强制写明 n 与独立性边界——这一点比多数团队的 benchmark 都诚实。
- 参考解进 reactor，CI 每次跑：答案真的被执行过。

扣分点：

- **n=1、单任务、同宿主隔离子代理**：只证明了"能跑通"，不能证明"比不用累土更快/更少错"——**没有对照组**。
- 歧义点归因由验收方回查得出，含主观成分；15/5 的划分如果再采一次样，可能变成 12/8。
- 规模化跑批仍写着"待行"，一年后会变成"从来没人做"。

## 7. 演进制度 · 3.5

证据：

- 双通道互不绑定，版本真源单点（根 pom），`check-skill.mjs` 强制 SKILL.md 与该值相等；`check-release-version.sh` 卡在发布前；Claude 版 skill 快照与 catalog 一致性也进了守门。
- 退役有出口：`deprecated` / `replaced_by` 是 catalog 的合法枚举，且进 CatalogIntegrity 的校验。

扣分点：

- **加一条答案动 24 个文件**（以 `cache` 那次提交实测），其中约 10 个是同步点：AGENTS、README、docs/index、views（已自动生成）、decisions/README、GLOSSARY、SKILL.md、catalog-snapshot。守门人只保证"改了要一致"，不保证"不用改"。
- 结论：现在"越用越厚"是**加法**，不是复利。厚到 30 条答案时，同步点会先于答案本身成为瓶颈。

## 三张工单（按杠杆排序）

**A. 一条"接入按序读"的清单页（治 3，最重要）**

把散在 README / 问题页 / 金样本里的接入硬事实收成一页，并按"先读什么"排序；同时改任务卡，把"允许阅读"改成"按序读 3 处"。
验收判据：重跑任务 01，A 类歧义点归零、总数 ≤8；否则算没修好。

**B. 四段式进机器（治 2、1，成本半天）**

`CatalogIntegrityTest` 加一个用例：每个 answered 条目指向的问题页必须含四个二级标题。顺手把 `access` 与 `allow-or-not` 的共用页拆开或写明"两条目共用一页"。

**C. 给实证补对照组与第二次采样（治 6，成本最高）**

同一任务卡，让另一路 agent 在**不提供累土**的条件下做一遍，比完成率与一次绿灯率。没有这一组，"确定性地基"只是主张；有了这一组，它才是数字。

### 一句话总结

强在"答案本身很难做坏"（形状 + 守护 + 落地），弱在"答案很难被找到"（可发现性）、"好多少没人量过"（实证）与"加一条越来越贵"（演进成本）。**先修可发现性，因为另外两项的读数都经过它。**
