## 在做什么

给人和 AI 的确定性后端地基：把实现不同系统时**反复出现、边界清楚的问题**，沉淀成一套**标准答案**。每条答案 = 五件套（问题页 + 代码 + 守护规则 + 金样本 + 目录条目），CI 机器验收——人拿到确定性，AI 拿到无歧义的生成目标。

### eval 实证：首次独立采样已完成（2026-09-27）

一次真正全新的子代理（工作目录在仓库之外、答案已物理剔除）跑完了任务 01。
**完整协议、四项数字与歧义点归因见 [eval/baselines.md](../eval/baselines.md)。**

一句话结果：**任务卡 6 条验收全过、一次绿灯、约 5 分 33 秒**；验收方独立补齐了它自己报告的两处缺口
（冷仓库解析、JDK 21 门槛）并额外做了真实 HTTP 打靶。

**最有价值的输出不是四个数字，是 20 条歧义点的归因**（逐条见 [eval/baselines.md](../eval/baselines.md) 的「歧义点归因」节）。
逐条回查文档后：**15 条不是文档缺失，而是文档已写却没被找到**——信息散落在
「问题页 + README 接入段 + 金样本」三处，新 agent 得自己拼。其中 1 条是**真漂移**：
README 宣称「引依赖即得 `/v3/api-docs`」，而 starter 把 springdoc 标了 `optional`——
不额外引依赖根本得不到端点，这是本次唯一一处「文档主动误导」，已随本次修复。

**后续（不阻塞收官）**：

1. 把 15 条可发现性问题当成**一个**问题修（而非 15 个）：新 agent 该看的入口不唯一——
   考虑给任务卡列的阅读顺序加一条「先读 README 接入段再做题」，或把接入要点收进一处；
2. B 类余下 4 条真缺口（属性表 / 无认证演示手法 / 他租户映射建议 / 依赖清单）；
3. 扩任务集到 N 条，才谈得上统计意义上的「规模化」。

**验收口径**：首次独立采样已登记，阶段三可宣布收官（规模化属后续增量，不再是门）。

### eval 实证：接入清单落地 + 任务卡 v2 复采 + 对照组首采（2026-10-26）

三件事同日完成（读数与歧义归因均见 [eval/baselines.md](../eval/baselines.md)，留痕在 `eval/runs/`）：

1. **接入清单**：[docs/INTEGRATION.md](INTEGRATION.md)——按执行顺序收拢散在三处的接入事实，
   上一节「后续」的第 1、2 条（15 条可发现性当一个修 + B 类 4 条真缺口）就此一并了结；
2. **任务卡 v2 复采**：6/6 · 一次绿灯 ✅ · 76 秒（缓存已热）· 26 条歧义——
   **「文档已写但没被找到」从 15 条归零**；v2 判据从此冻结；
3. **对照组首采**：同一任务不用累土（禁止引入任何非 Spring 官方库）——
   5/5 · **一次绿灯 ❌**（Initializr 版本串 Central 不存在）· 287 秒 · 13 条歧义。
   **第一次拿到「比不用强多少」的对照读数**：一次绿灯的差距是结构性的（版本/坐标类猜谜
   被标准答案锁死）；对照组自己发明了一套错误方言——两个服务两种方言，正是决策坍缩要消灭的。

诚实边界照登：双方均 n=1、同宿主隔离子代理、禁得掉依赖禁不掉训练记忆；时长受脚手架影响。

**伴随的制度修复**：文档守卫改按声明的资产面取文件（工作目录 ≠ 仓库内容，外来文件免疫）、
四段式进机器（answered 问题页缺段即红）、access 拿到独立问题页。
